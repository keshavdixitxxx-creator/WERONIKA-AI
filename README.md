# Weronika AI

Weronika is a voice-and-text assistant. Her conversation UI is served by the web app, and replies are generated by the hosted cloud brain.

## Current scope

- **Cloud-brain chat:** text and voice conversations use the hosted brain endpoint (`/api/public/brain`).
- **Browser-only chat history:** saved in this browser's local storage.
- **Local worker for device automation:** messaging and reply watch run through `weronika-py` on your own computer because they use your signed-in browser session. Without it, the orb stays a cloud-brain chat and nothing is read, typed, or sent.
- **Orb controls:** visual orb settings and camera gestures affect only the orb; they do not control the computer.

## Run the web app

```bash
bun install
bun run dev
```

The same scripts can be run with npm (`npm install`, `npm run dev`). The orb's public-site launcher runs in the user's browser and does not need the Python worker or a batch file. Existing direct-message automation still depends on the separate local Python worker today.

To build and preview a production build:

```bash
npm run build
npm run preview
```

The cloud brain credentials remain on the server. The browser sends conversation requests to `/api/public/brain`; it does not call a local Python service.

## Reply watch (WhatsApp / Telegram)

The orb has a **◎ REPLY WATCH** panel (⚙ SETTINGS → Tools) and a matching chat vocabulary. Weronika reads
only the chats you name, in the same local browser window you sign in to, and notices
when someone messaged you and you have not answered. She then either asks you what to
reply or drafts a suggested reply — and still waits for `confirm send` before the
exact text is typed and sent. Replies can also use a file from the local workspace
(for example a leave policy) or a one-time code you want to forward. A **✧ SKILLS**
panel, next to it under ⚙ SETTINGS → Tools, lists exactly what the local worker
implements and the gaps it will not fake.

This needs the local Python worker (`weronika-py`, started with `start.bat`), because
the browser sessions stay on your computer. The hosted web page alone cannot read
messages, and no platform API is used: WhatsApp has no personal-account chat API and
Telegram user accounts should use the official Bot API, so the worker reads the visible
web session you already signed in to. Instagram's web app has no dependable message
list, so reading DMs is refused there rather than guessed. See
[weronika-py/README.md](weronika-py/README.md) for the full flow and limits.

## Browser tasks (search, open, play, post)

The orb can also plan and run browser steps: search the web, open a specific result,
read the page back, play a video or song on YouTube, and — only after your explicit
`confirm` — type and submit a comment, like, or subscribe. Complex phrasing is broken
into ordered steps by the hosted brain and shown before anything runs. Naming Edge or
Chrome (“open github in chrome”) opens the address in your own browser instead.
These run through the local worker; see [weronika-py/README.md](weronika-py/README.md)
for the step list and limits.

## Gmail (optional OAuth integration)

Gmail is disconnected until an operator configures Google OAuth. In a Google Cloud project, enable the Gmail API, create a Web application OAuth client, and register the exact redirect URI `https://YOUR_APP_ORIGIN/api/gmail/callback` (use the matching `http://localhost:PORT/api/gmail/callback` for local development). Set these server-only environment variables:

```text
GOOGLE_OAUTH_CLIENT_ID=...
GOOGLE_OAUTH_CLIENT_SECRET=...
GOOGLE_OAUTH_REDIRECT_URI=https://YOUR_APP_ORIGIN/api/gmail/callback
```

Never expose the client secret to browser code. The app requests only `gmail.readonly` and `gmail.send`. Inbox listing shows message metadata; message bodies are fetched only for messages explicitly selected by the user. Their content is sent to the hosted AI only after the user chooses **SUMMARIZE SELECTED** or **DRAFT REPLY**. Sending requires a server-prepared review token and a second explicit confirmation of the unchanged recipient and exact reply body. No inbox organization, deletion, or modification scope is requested.

OAuth state is one-time and browser-bound. Gmail access tokens and prepared-send data are held in process memory only, never written to a database or local storage. This deliberately ephemeral implementation expires/requires reconnect on token/process expiry; it is not suitable for horizontally scaled or serverless deployments unless a secure shared ephemeral session store is added. Selected-email AI processing also requires the current deployment's server-side `LOVABLE_API_KEY`; without it, Gmail requests fail closed instead of relaying email content to an older brain endpoint without Gmail-specific safety instructions. No Google credentials are configured in this checkout, so the live OAuth round trip has not been tested.

## Tests

```bash
npm run test
```

The JavaScript suites check the cloud-brain conversation path and keep the Gmail permissions and selected-message/send-review policy from regressing. Media routes are checked to remain disabled/local-only.
